# ADR-001: Capas simples para la persistencia; el seam de notificación ya cubre el próximo cambio conocido

## Estado

Aceptado — 2026-11-10

## Contexto

El sistema de solicitudes de reembolso ya integra tres patrones de comportamiento: Chain of Responsibility (validación), Strategy (cálculo por categoría) y Observer (notificación). Antes de seguir creciendo corresponde decidir si el proyecto completo debe migrar a arquitectura Hexagonal —puertos e interfaces intermedias para todas sus dependencias externas— o mantenerse en capas simples.

El criterio de la Guía (sección 6.2) es que Hexagonal vale la pena "en sistemas que sobrevivirán 3 años o más con cambios de infraestructura". Son dos condiciones, y se evalúan por separado para cada dependencia externa con los datos de este proyecto:

| Dependencia externa | ¿Vivirá 3 años o más? | ¿Hay un cambio de infraestructura previsto? |
|---------------------|-----------------------|---------------------------------------------|
| **Persistencia** (JPA + H2) | Probablemente sí: reemplaza la hoja de cálculo de Finanzas | **No.** No existe ningún plan de cambiar el motor de base de datos |
| **Notificación a Contabilidad** | Sí | **Sí, con fecha.** Contabilidad anunció para el próximo trimestre una integración por API externa para el pago de las solicitudes aprobadas |

Datos concretos del código que pesan en la decisión:

- `SolicitudReembolsoService` es el **único** cliente de `RepositorioSolicitudesJpa` y usa tres operaciones: `findByEmpleadoIdAndEstado`, `findById` y `save`.
- El dominio (`SolicitudReembolso`) ya no importa nada de JPA: el mapeo está en `META-INF/orm.xml`. El beneficio principal que daría un puerto —proteger el dominio de la tecnología de persistencia— ya se obtuvo sin él.
- El paquete `procesamiento` (los tres patrones) no conoce el repositorio: `ValidadorDuplicados` recibe la lista de pendientes ya cargada. Sus pruebas unitarias corren sin base de datos y sin Spring.
- El servicio no conoce a ningún notificador concreto: recibe `List<ObservadorCambioEstado>`.

## Alternativas evaluadas

### A. Hexagonal completa

Introducir el puerto `RepositorioSolicitudes` con un adaptador JPA, y un puerto de salida adicional para la notificación a Contabilidad.

- **A favor:** simetría (todas las dependencias externas detrás de un puerto); el servicio se podría probar con un repositorio falso en memoria.
- **En contra:** el puerto de persistencia tendría exactamente una implementación y un cliente; no hay un segundo motor ni un plan de tenerlo, así que sería una abstracción especulativa (YAGNI). Para que el adaptador aportara algo distinto a reenviar llamadas habría que duplicar el modelo (entidad JPA + mapper), es decir, unas cuatro clases nuevas sin ningún caso de uso detrás. Las pruebas del servicio tampoco lo necesitan: la prueba de integración ya corre sobre H2 en memoria en segundos.

### B. Capas simples sin ninguna consideración adicional

Dejar todo como está y no evaluar la notificación.

- **A favor:** cero cambios.
- **En contra:** ignora el único cambio de infraestructura que sí tiene fecha. Había que verificar, no asumir, que el diseño actual lo soporta.

### C. Capas simples para persistencia + seam existente para notificación (elegida)

No agregar el puerto de persistencia, y confirmar que `ObservadorCambioEstado` ya es el punto de extensión que la integración de Contabilidad necesita.

## Decisión

**Persistencia: capas simples.** `SolicitudReembolsoService` sigue dependiendo directamente de `RepositorioSolicitudesJpa`, sin una interfaz de puerto intermedia. De las dos condiciones del criterio de la Guía solo se cumple una: el sistema vivirá años, pero no hay ningún cambio de infraestructura de persistencia previsto. Un puerto hoy sería una abstracción sin caso de uso.

**Notificación: no se introduce ningún cambio.** Aquí sí se cumplen las dos condiciones, y por eso hace falta un seam; pero ese seam ya existe: `ObservadorCambioEstado` cumple el papel de puerto de salida. Cuando llegue la API de Contabilidad, la integración será una implementación de `ObservadorCambioEstado` que reemplaza la lógica interna de `NotificadorContabilidad` (hoy un `System.out.println`) por la llamada externa. No se modifican `SolicitudReembolsoService`, `NotificadorEmpleado` ni `NotificadorAuditoria`. Agregar además un puerto específico "para pagos" duplicaría una abstracción que ya está.

No se escribe hoy ningún código para esa integración: el contrato de la API aún no se conoce, y diseñar contra un contrato imaginado sería tan especulativo como el puerto de persistencia.

## Consecuencias

### Positivas

- No se agregan interfaces, entidades duplicadas ni mappers de persistencia sin un caso de uso real que los justifique.
- El único cambio de infraestructura con fecha conocida (integración de Contabilidad) ya tiene su punto de extensión listo y probado: la prueba de integración verifica que el servicio notifica a todos los observadores sin conocerlos.
- Los límites que sí importan quedan verificados de forma automática con ArchUnit (`ReglasArquitectura`): `procesamiento` no depende de infraestructura, adaptadores ni JPA, y el controlador solo accede al servicio y al dominio.
- El código que hay que leer para entender una solicitud de punta a punta es corto: controlador → servicio → repositorio.

### Negativas

- Si en el futuro se necesita cambiar de motor de base de datos, el puerto de persistencia deberá introducirse retroactivamente. Se acepta esa deuda técnica de forma consciente; el costo está acotado porque el repositorio tiene un solo cliente y tres operaciones.
- `SolicitudReembolsoService` no se puede probar de forma unitaria sin simular `RepositorioSolicitudesJpa` o levantar H2; hoy se cubre con la prueba de integración.
- Un revisor que espere simetría total (puertos en todas las dependencias externas) puede interpretar la asimetría como inconsistencia si no lee este ADR.
- Los observadores se ejecutan de forma síncrona y en secuencia dentro de `cambiarEstado`. Con notificadores locales es irrelevante, pero cuando `NotificadorContabilidad` llame a una API externa, una caída o lentitud de esa API afectaría la respuesta al usuario y a los observadores que corren después. Este ADR no lo resuelve porque todavía no hay API contra la cual medirlo; queda registrado como lo primero a revisar cuando llegue la integración.

## Señales para reconsiderar

- **Persistencia:** aparece un requisito real de un segundo origen de datos (otro motor, un servicio externo de solicitudes, lectura desde el ERP), o un segundo cliente del repositorio con necesidades distintas a las del servicio.
- **Notificación:** se firma el contrato de la API de Contabilidad. En ese momento se decide con datos si basta con reemplazar la implementación del observador o si hace falta aislar fallos (reintentos, ejecución asíncrona).
